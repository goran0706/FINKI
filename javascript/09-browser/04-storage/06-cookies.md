# HTTP Cookies and Secure Cookie Management

## Overview of HTTP Cookies

HTTP cookies are small pieces of data sent by a server via the `Set-Cookie` response header and automatically stored by
the browser. Unlike `localStorage` or `sessionStorage`, cookies are **automatically included by the browser in
subsequent HTTP requests** to the same domain, making them uniquely suited for server-side session identification and
authentication.

| Feature            | Cookie Characteristic                                                                    |
|:-------------------|:-----------------------------------------------------------------------------------------|
| **Data Format**    | Key-value string pairs                                                                   |
| **Capacity Limit** | Typically ~4KB per cookie                                                                |
| **Persistence**    | Configurable via `Expires` or `Max-Age` (session cookies expire when the browser closes) |
| **Transmission**   | Automatically sent with every HTTP request to the matching domain                        |

## Cookie Fundamentals

HTTP cookies serve as the backbone for maintaining state over the stateless HTTP protocol. Because HTTP requests are
independent, cookies allow servers to remember user preferences, login states, and tracking sessions across page
transitions without relying on client-side storage objects.

## Creating Cookies

Cookies can be generated by a server response using the `Set-Cookie` header or manipulated directly on the client side
using `document.cookie` (provided the cookie lacks the `HttpOnly` restriction).

### Creating Cookies via Server Response

```http
Set-Cookie: user_session=abc123xyz; Domain=example.com; Path=/dashboard; Secure; HttpOnly; SameSite=Strict; Max-Age=86400
```

### Creating Cookies via Client-Side JavaScript

```javascript
// Setting a non-sensitive cookie client-side
document.cookie = "user_pref=dark_mode; max-age=31536000; path=/; SameSite=Lax";
```

## Reading Cookies

Reading cookies on the client side involves accessing `document.cookie`, which returns a single string containing all
accessible, non-HttpOnly cookies separated by semicolons.

```javascript
// Reading cookies (returns a single string containing all accessible cookies separated by semicolons)
const allCookies = document.cookie;
console.log(allCookies); // "user_pref=dark_mode; tracking_id=98234"
```

## Cookie Expiration

By default, cookies are treated as session cookies, meaning they are automatically deleted when the user closes their
browser window or tab. To make cookies persist across browser restarts, you must define an explicit lifespan using
`Max-Age` or `Expires`.

* **`Max-Age`**: Specifies the lifetime of the cookie in seconds (e.g., `Max-Age=3600` lasts for one hour). Setting
  `Max-Age=0` or a negative value deletes the cookie instantly.
* **`Expires`**: Specifies a precise HTTP-date timestamp indicating when the cookie should become invalid.

```javascript
// Deleting a cookie by setting its expiration date/max-age to the past
document.cookie = "user_pref=; max-age=0; path=/";
```

## HttpOnly Cookies

The `HttpOnly` attribute is a critical security flag that **prevents client-side JavaScript (via `document.cookie`) from
accessing the cookie**.

* **Primary Defense:** Mitigates Cross-Site Scripting (XSS) data theft by ensuring that even if an attacker successfully
  injects malicious scripts into your application, they cannot read session tokens or authentication credentials.
* **Usage:** Always applied to sensitive session identifiers and JWT authentication tokens.

## Secure Flag

The `Secure` attribute ensures that the browser will **only transmit the cookie over encrypted HTTPS connections**,
preventing cleartext transmission over insecure HTTP networks.

* **Mitigation:** Protects session IDs from Man-in-the-Middle (MitM) eavesdropping on public Wi-Fi or unencrypted legacy
  networks.
* **Usage:** Mandatory for any cookie handling authentication, personal data, or financial transactions.

## SameSite Cookies

The `SameSite` attribute controls whether cookies are sent during cross-site requests, providing robust protection
against Cross-Site Request Forgery (CSRF) attacks.

* **`SameSite=Strict`**: Cookies are never sent on cross-site requests (highest security for sensitive banking or
  administrative portals).
* **`SameSite=Lax`**: Cookies are withheld on cross-site subrequests (like images or frames) but sent when a user
  navigates to the origin site via a standard top-level link.
* **`SameSite=None`**: Cookies are sent on all cross-site requests (mandatory `Secure` attribute required; commonly used
  for third-party widgets or federated authentication).

## Use Cases

* **Server-Driven Authentication:** Storing encrypted session IDs or JSON Web Tokens (JWTs) in `HttpOnly` and `Secure`
  cookies to authenticate users safely across requests.
* **CSRF Defense Systems:** Pairing `SameSite=Strict` cookies with anti-CSRF synchronizer tokens to block unauthorized
  cross-origin mutations.
* **Secure State Configuration:** Storing non-sensitive UI settings or localization flags that need to be read instantly
  by server-side rendering (SSR) engines.

## Best Practices

* **Always Use `HttpOnly` for Auth Tokens:** Never expose sensitive session identifiers, credentials, or JWTs to
  client-side JavaScript via `document.cookie` to mitigate XSS-based theft.
* **Enforce `Secure` on Production Environments:** Always pair cookies containing sensitive data with the `Secure` flag
  to prevent cleartext transmission over insecure HTTP networks.
* **Choose the Right `SameSite` Policy:** Default to `SameSite=Lax` for standard web applications, or `SameSite=Strict`
  for highly sensitive user dashboards to completely block CSRF vectors.
* **Respect the 4KB Size Limit:** Keep cookie payloads lightweight; do not use cookies to store heavy application data,
  files, or large JSON objects.
* **Explicitly Define Scope (`Path` and `Domain`):** Restrict cookies to precise paths and domains to minimize surface
  area exposure across unrelated endpoints.
* **Never Store Unencrypted Personally Identifiable Information (PII):** Exclude clear-text sensitive user data such as
  real names, home addresses, or phone numbers from cookie headers.
* **Sanitize Retrieved Cookie Data:** Treat all values read from client-accessible cookies as untrusted input before
  rendering them into the DOM or processing application logic.
* **Handle Cookie Quota Limits Properly:** Ensure application logic does not exceed browser domain cookie counts or
  total size limits, which can cause silent truncation.
* **Implement Versioned Cookie Names:** Prefix or version cookie keys when modifying application auth schemas or session
  data structures across updates.
* **Clean Up Expired Cookies Promptly:** Explicitly expire legacy cookies during logout flows or version upgrades by
  setting `Max-Age=0` or past expiration dates.
* **Guard Against Private Browsing Failures:** Handle environments where strict cookie blocking policies or privacy
  settings restrict cookie persistence.
* **Validate Cookie Availability:** Check for browser storage settings before executing flows that depend on persistent
  cookie configurations.
* **Namespace Custom Cookie Keys:** Prefix application-specific cookies to prevent naming collisions with third-party
  scripts or injected browser extensions.
* **Enforce HTTPS Everywhere:** Ensure all target endpoints use TLS/SSL so `Secure` cookies are never dropped or exposed
  during insecure redirects.
* **Never Store Function References:** Avoid serializing closures, functions, or complex object graphs into cookie
  string values.
* **Expire Transient State Manually:** Attach explicit lifespan properties or short max-age parameters to temporary UI
  preference cookies.
* **Encrypt Sensitive Non-Token State:** Apply robust cryptographic encryption before storing semi-sensitive state
  configurations inside client-accessible cookies.
* **Review Cookie Access Permissions:** Ensure third-party scripts loaded via external CDNs do not access unflagged
  non-HttpOnly cookies.
* **Avoid Storing Large Binary Data:** Never attempt to stuff binary buffers, blobs, or heavy media assets into cookie
  strings.
* **Implement Secure Cookie Wrappers:** Build centralized utility modules for setting and parsing cookies to enforce
  secure defaults automatically.
* **Monitor Cookie Header Sizes:** Keep total HTTP request header sizes well below server drop thresholds by limiting
  the number of active cookies per domain.
* **Test Cookie Attributes in Automation:** Verify that `Secure`, `HttpOnly`, and `SameSite` flags are correctly
  validated in automated security testing pipelines.
* **Avoid Storing Mutable Derived State:** Restrict cookie payloads strictly to raw session identifiers or minimal
  configuration toggles.
* **Protect Against Cookie Injection:** Ensure cookie values set via user input are strictly validated and URL-encoded
  to prevent header injection vulnerabilities.
* **Migrate Legacy Cookie Formats Gracefully:** Support backward-compatible parsing logic when updating cookie naming
  conventions or value formats.
* **Disable Cookie-Dependent Features in Restricted WebViews:** Implement defensive guards to prevent runtime crashes
  when running inside constrained mobile webviews with disabled cookies.
* **Audit Cookie Footprint Periodically:** Run automated security scans and codebase audits to detect abandoned or
  redundant cookies.
* **Avoid Storing Sensitive Data in Subdomain-Accessible Cookies:** Restrict cookie domain scopes strictly to prevent
  less secure sibling subdomains from reading sensitive parent cookies.
* **Pair SameSite=None with Secure:** Ensure any cookie using `SameSite=None` explicitly includes the `Secure` flag to
  comply with modern browser security specifications.
